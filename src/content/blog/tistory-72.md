안녕하세요! 오늘은 백엔드 개발자라면 한 번쯤 마주치게 되는(혹은 이미 당하고 있을지도 모르는) 무시무시한 녀석, **'N+1 문제'**에 대해 이야기해 보려고 합니다.

분명 로컬 환경에서는 API가 날아다녔는데, 실서버에 배포하고 데이터가 쌓이기 시작하니 응답 속도가 거북이🐢가 되어버린 경험 있으신가요? DB 스펙업을 고민하기 전에, 혹시 내 코드에 '조용한 암살자'가 숨어있는 건 아닌지 확인해 봐야 합니다.

![](/blog/images/tistory-72/img1.png)

---

백엔드 서버의 응답 속도를 갉아먹는 조용한 암살자, 'N+1 문제'의 원인과 해결 방법을 알아봅니다. Node.js와 Prisma 환경에서 지연 로딩(Lazy Loading)이 만드는 성능 병목을 이해하고, 즉시 로딩(Eager Loading)을 활용해 쿼리 성능을 비약적으로 끌어올리는 꿀팁을 햄버거집 알바생 비유로 아주 쉽게 정리했습니다. 서버 성능 최적화에 관심 있는 주니어 개발자라면 꼭 확인해 보세요!

## 🍔 N+1 문제, 도대체 그게 뭔데? (feat. 비효율 끝판왕 알바생)

N+1 문제는 Prisma, TypeORM, JPA 등 ORM(Object-Relational Mapping)을 사용할 때 아주 흔하게 겪는 성능 저하 현상입니다.

어려운 기술 용어 대신, **'식당에서 비효율적으로 일하는 햄버거집 알바생'**을 상상해 볼까요?

1. 손님 10명이 단체로 와서 "여기 햄버거 세트 10개 주세요"라고 주문합니다. **(1번의 요청)**
2. 알바생이 주방에 가서 햄버거 10개를 주문합니다.
3. 그런데 이 알바생... 손님 1명, 1명에게 다시 다가가서 "음료는 뭘로 하시겠어요?"라고 10번 따로 물어보고, 주방에 10번을 추가로 왔다 갔다 합니다. **(N번의 추가 요청)**

총 11번(1 + 10)이나 주방을 오가게 되죠. 처음 주문받을 때 "햄버거 10개, 음료는 콜라 5, 사이다 5요!"라고 **한 번에** 주방에 전달했다면 훨씬 빨랐을 텐데 말입니다.

이 알바생이 바로 우리의 ORM이고, 주방이 데이터베이스(DB)입니다.

---

## 💻 실제 코드로 보는 N+1 문제 (혈압 주의)

사용자(User) 목록을 불러오고, 각 사용자가 작성한 게시글(Post) 목록을 화면에 보여줘야 하는 상황을 가정해 봅시다.

### ❌ 나쁜 예: 지연 로딩(Lazy Loading)의 함정

```
// 1. 먼저 DB에서 사용자 10명을 조회합니다. (1번의 쿼리 발생)
// SELECT * FROM User LIMIT 10;
const users = await prisma.user.findMany({ take: 10 });

// 2. 반복문을 돌면서 각 유저의 게시글을 따로따로 조회합니다. (N번의 쿼리 발생)
const usersWithPosts = await Promise.all(
  users.map(async (user) => {
    // SELECT * FROM Post WHERE userId = ?; -> 이 쿼리가 10번 실행됨!
    const posts = await prisma.post.findMany({ where: { userId: user.id } });
    return { ...user, posts };
  })
);
```

결과적으로 사용자 10명의 정보를 온전히 가져오기 위해 데이터베이스에 **총 11번(1 + 10)의 질문(Query)**을 던지게 됩니다. 만약 조회해야 할 사용자가 1,000명이라면? 1,001번의 쿼리가 발생해서 서버와 DB가 엄청나게 느려지고 결국 뻗어버릴 수도 있습니다. 😱

---

### 💡 왜 이런 일이 발생할까요?

ORM은 기본적으로 메모리를 아끼고 효율적으로 동작하기 위해 **'진짜로 데이터가 필요해질 때까지'** 연관된 데이터를 가져오는 것을 미룹니다. 이를 지연 로딩(Lazy Loading)이라고 하는데요. 단일 데이터 조회 시에는 유리하지만, 위처럼 목록(List)을 순회하며 연관 데이터를 찾을 때는 N+1 문제의 주범이 됩니다.

## 🛠️ 즉시 로딩(Eager Loading)으로 한 방에 해결하기!

해결책은 간단합니다. 햄버거 주문을 할 때 음료까지 한 번에 주문하듯, 처음부터 **필요한 데이터를 한 번에 묶어서 가져오라고 명확하게 지시(JOIN)**하면 됩니다.

### ✅ 좋은 예: Prisma include 활용하기

```
// "사용자 가져올 때, 이 사용자가 작성한 글도 한 번에 다 묶어서(JOIN) 가져와 줘!"
const usersWithPosts = await prisma.user.findMany({
  take: 10,
  include: {
    posts: true, 
  },
});
```

이렇게 처리하면 ORM 내부적으로 JOIN 연산을 사용하거나 IN 연산자(WHERE userId IN (1,2,3...))를 사용하여, 데이터베이스에 단 1번(혹은 2번)의 쿼리만 날리게 됩니다. 처리 속도가 비약적으로 빨라지는 것은 당연하겠죠?

## 📝 짤막 회고 (KPT)

- **Keep (유지할 점):** 서버 성능이 느려졌을 때 단순히 하드웨어 스펙업을 고민하기보다, 쿼리 레벨의 병목(N+1)을 먼저 의심하고 논리적인 원인을 찾아내려 한 점.
- **Problem (문제점):** ORM이 알아서 쿼리를 잘 짜줄 것이라고 맹신하여, 실제 DB로 날아가는 SQL 로그를 꼼꼼히 모니터링하지 못했던 점.
- **Try (시도할 점):** 로컬 개발 환경에서는 ORM의 쿼리 로깅 옵션(예: Prisma의 log: ['query'])을 반드시 켜두고, API를 개발할 때마다 불필요한 쿼리가 중복 발생하지 않는지 콘솔 창을 확인하는 습관 들이기!

데이터베이스 설계와 백엔드 API를 만들 때, 이 N+1 문제만 잘 체크하고 예방해도 응답 속도를 엄청나게 높일 수 있습니다. 오늘 작성한 코드가 내일의 서버를 살립니다. 모두 즐코하세요! 👨‍💻👩‍💻
