안녕하세요.

**"API가 200 OK를 뱉는다고 끝난 게 아니다."**

이번 중고차 계약 관리 서비스 프로젝트를 진행하며 뼈저리게 느낀 점입니다. 백엔드 개발자로서 단순히 서버 로직만 구현하는 것을 넘어, **클라이언트(프론트엔드)와의 연동 과정에서 발생하는 문제를 직접 디버깅하고 해결**하며 서비스의 완성도를 높였던 경험을 공유합니다.

### 1. 프로젝트 개요

- **프로젝트명:** 중고차 계약 관리 서비스 (Used Car Contract Management Service)
- **Github:** [Link to Repository](https://github.com/Leon97-dev/nb6-team3-project)
- **소개:** 차량, 고객, 미팅 정보를 통합 관리하고 계약 상태를 **칸반 보드(Kanban Board)** 형태로 시각화하여 업무 효율성을 높인 백엔드 서비스입니다.
- **개발 환경:** Node.js, TypeScript, Express, Prisma, Swagger
- **특이 사항:** 백엔드 기능 검증을 위해 사전에 제공된 프론트엔드 코드를 활용했으며, 이 과정에서 **프론트엔드 로직 수정 및 디버깅**을 통해 API 연동을 주도적으로 완수했습니다

---

### 2. 담당 역할 (Role & Responsibility)

저는 이번 프로젝트에서 **계약(Contract) 도메인의 핵심 로직**을 담당했습니다.

- **Core Logic:** 계약의 라이프사이클(등록, 수정, 삭제, 조회) 전반을 관리하는 API 개발
- **DB Design:** Prisma 기반의 관계형 데이터베이스 스키마 설계 및 마이그레이션
- **Full-stack Debugging:** API 연동 시 발생하는 클라이언트 측 오류를 직접 분석하고 수정
- **Documentation:** Swagger를 통한 API 명세화 및 팀 내 공유

---

### 3. 기술적 의사결정 및 코드 품질

단순히 돌아가는 코드가 아닌, **유지보수성(Maintainability)**과 **데이터 무결성(Data Integrity)**을 최우선으로 고려했습니다.

#### 1) 계층형 아키텍처 (Layered Architecture)

Controller - Service - Repository로 역할을 명확히 분리했습니다. 비즈니스 로직이 Express 프레임워크에 종속되지 않도록 하여 독립적인 테스트와 수정이 용이하도록 설계했습니다.

![](/blog/images/tistory-56/img1.jpg)

#### 2) Superstruct를 활용한 런타임 검증

TypeScript의 정적 타입 체크만으로는 부족하다고 판단하여, superstruct 라이브러리를 도입했습니다. 런타임에서 req.body로 들어오는 데이터를 엄격하게 검증하여, 잘못된 데이터가 서비스 레이어로 진입하는 것을 **원천 차단(Fail Fast)**했습니다.

#### 3) Prisma Select 최적화 (Over-fetching 방지)

findMany 등을 사용할 때 필요한 필드만 정확히 조회(select)하도록 구현했습니다. 이를 통해 불필요한 데이터 전송을 줄이고 DB 부하를 최소화하여 응답 속도를 개선했습니다.

![](/blog/images/tistory-56/img2.jpg)

### 4. 핵심 트러블 슈팅 (Troubleshooting: STAR)

프로젝트 진행 중 겪었던 주요 기술적 난관과 이를 해결한 과정입니다. 특히 **백엔드 개발자가 클라이언트 이슈를 어떻게 해결했는지**에 집중해 주세요.

#### ① 필수 데이터 누락으로 인한 서버 멈춤 현상

- **문제(Situation):** 계약 등록 시 contractPrice(계약금)가 null로 전달되어 백엔드 서버가 멈추는(DB Lock/Timeout 추정) 현상이 발생했습니다.
- **원인(Task):** 로그 분석 결과, 차량 정보 조회 시 가격 정보가 누락되어 발생한 문제였습니다.
- **해결(Action):** contract-repository의 조회 로직을 수정하여 price 필드를 필수로 가져오도록 변경하고, Service 계층에서 이를 명시적으로 할당했습니다.
- **결과(Result):** 데이터 흐름을 정상화하여 서버 멈춤 현상을 완벽하게 제거했습니다.

#### ② "삭제 실패?" 클라이언트 로직 디버깅 (Full-stack Debugging)

- **문제(Situation):** 백엔드 삭제 API는 200 OK를 반환하고 DB에서도 삭제되었으나, 화면에서는 '삭제 실패' 메시지가 출력되었습니다.
- **해결(Action):** 백엔드 문제가 아님을 확신하고 제공된 프론트엔드 코드(useDeleteContract.ts)를 분석했습니다. 상태 갱신 조건문(!queryData)의 논리적 오류를 발견하고, if (!queryData || !queryData[status])로 예외 처리를 강화했습니다.
- **결과(Result):** 실제 데이터 처리 결과와 UI 메시지를 일치시켜 사용자 혼란을 방지했습니다. **"내 코드는 문제없어"라고 단정 짓지 않고 전체를 본 덕분**입니다.

#### ③ 500 에러 방어를 위한 방어적 프로그래밍

- **문제(Situation):** 프론트엔드에서 Optional 필드인 fileUrl을 보내지 않을 경우 백엔드에서 500 에러가 발생했습니다.
- **해결(Action):** 클라이언트가 값을 보내주길 기대하기보다 백엔드에서 방어하는 것이 맞다고 판단했습니다. Controller 단에서 null/undefined일 경우 빈 문자열("")로 치환하는 전처리 로직을 추가했습니다.
- **결과(Result):** 외부 입력값에 대한 의존성을 낮추고 **API의 견고함(Robustness)**을 확보했습니다.

#### ④ Enum 표기법 차이와 매핑(Mapping) 전략

- **문제(Situation):** 프론트엔드(CamelCase, carInspection)와 백엔드 DB(SnakeCase, CAR\_INSPECTION)의 표기법 차이로 상태 변경 API가 동작하지 않았습니다.
- **해결(Action):** 이미 작성된 프론트엔드 코드를 전면 수정하는 대신, 백엔드 진입점에서 **매핑(Mapping) 상수**를 도입하여 요청 값을 내부 DB 규격에 맞게 변환 처리했습니다.
- **결과(Result):** 시스템 간 호환성 문제를 해결하고 드래그 앤 드롭 기능을 정상화했습니다.

### 5. 협업 및 향후 개선 사항

**협업 방식**

- **효율적인 초기 세팅:** 과도한 설계보다는 핵심 기능 위주의 공통 설정을 제안하여 팀원들의 부담을 줄였습니다.
- **Daily Sync:** 매일 회의를 통해 DB 변경 사항을 공유하여 작업 간 충돌을 방지했습니다.

**Future Improvements**

- **트랜잭션(Transaction) 강화:** 현재 순차적으로 실행되는 로직들에 Prisma.$transaction을 적용하여 원자성(Atomicity)을 보장할 예정입니다.
- **Soft Delete 도입:** 데이터 보존 및 감사 로그 활용을 위해 deletedAt 컬럼을 활용한 논리적 삭제로 전환을 고려 중입니다.
- **검색 성능 최적화:** contains 검색의 성능 저하를 방지하기 위해 DB 인덱싱(Indexing) 적용이 필요합니다.

### 마치며

이번 프로젝트는 **"백엔드 개발자의 책임 범위는 어디까지인가?"**에 대해 깊이 고민하게 해 준 시간이었습니다.

API만 잘 만든다고 서비스가 완성되는 것은 아니었습니다. 클라이언트의 코드를 이해하고, 데이터가 흘러가는 전체 파이프라인을 디버깅할 수 있을 때 비로소 **안정적인 서비스**가 탄생한다는 것을 배웠습니다. 앞으로도 **숲을 보는 백엔드 개발자**로 성장하겠습니다.
