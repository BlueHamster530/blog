안녕하세요.

백엔드 개발을 공부하다 보면 데이터베이스(DB)가 단순히 데이터를 저장하는 창고가 아니라는 것을 깨닫게 됩니다.

DB는 데이터가 엉키지 않게 감시하는 **엄격한 규칙(무결성)**을 가지고 있고, DB의 변경 사항을 역사처럼 기록하는 **관리 시스템(마이그레이션)**을 가지고 있습니다.

오늘은 관계형 데이터베이스(RDB)를 지탱하는 두 가지 핵심 기둥, **무결성(Integrity)**과 **마이그레이션(Migration)**에 대해 아주 자세히 알아보겠습니다.

![](/blog/images/tistory-69/img1.png)

---

### 1. 데이터 무결성 (Data Integrity): 데이터의 수호자

데이터 무결성이란 **"데이터의 정확성(Accuracy)과 일관성(Consistency)을 유지하고, 결손이나 부정합이 없도록 보증하는 것"**을 말합니다.

쉽게 말해, 데이터베이스에 **쓰레기 데이터(Garbage Data)**가 들어오지 못하게 막는 **'수문장'**이자 **'방어막'**입니다. 만약 무결성이 깨지면, 존재하지 않는 회원이 물건을 주문하거나, 나이가 -5살인 사람이 저장되는 등 치명적인 오류가 발생합니다.

RDB에서는 크게 3가지 무결성 제약 조건을 통해 데이터를 보호합니다.

#### ① 개체 무결성 (Entity Integrity)

- **핵심:** "모든 테이블은 각 행(Row)을 식별할 수 있는 고유한 ID가 있어야 한다."
- **규칙:** 기본 키(Primary Key, PK)로 선택된 컬럼은 **NULL일 수 없고, 중복된 값을 가질 수 없습니다.**
- **예시:**
  - 국민에게 주민등록번호가 없다면? (NULL 불가)
  - 나와 똑같은 주민등록번호를 가진 사람이 또 있다면? (중복 불가)
  - DB에서도 User 테이블의 id는 반드시 존재해야 하며, 유일해야 합니다.

#### ② 참조 무결성 (Referential Integrity)

- **핵심:** "참조하는 데이터는 반드시 실제로 존재해야 한다."
- **규칙:** 외래 키(Foreign Key, FK) 값은 **NULL이거나, 참조하는 부모 테이블의 기본 키(PK) 값과 동일**해야 합니다.
- **예시:**
  - '주문 테이블'에 주문자\_id가 100번으로 적혀 있습니다.
  - 그런데 실제 '회원 테이블'을 찾아보니 100번 회원이 없습니다.
  - 이런 데이터(고아 레코드)가 생기지 않도록 막는 것이 참조 무결성입니다.
  - *특징:* 부모 데이터(회원)를 삭제하려고 할 때, 자식 데이터(주문)가 남아있다면 삭제를 막아주는 역할도 합니다.

#### ③ 도메인 무결성 (Domain Integrity)

- **핵심:** "데이터는 정해진 범위와 형식 내에서만 움직여야 한다."
- **규칙:** 특정 컬럼에 입력되는 값은 정의된 **데이터 타입, 길이, 허용 범위(Check)** 등을 만족해야 합니다.
- **예시:**
  - 성별 컬럼: '남(M)', '여(F)'만 허용 (갑자기 '감자' 같은 값이 들어올 수 없음)
  - 가격 컬럼: 숫자만 허용하며, 0보다 커야 함 (음수 불가)
  - 학점 컬럼: 0.0 ~ 4.5 사이의 값만 허용

### 2. 데이터베이스 마이그레이션 (Migration): DB의 타임머신

개발자 사이에서 마이그레이션은 문맥에 따라 두 가지 의미로 쓰입니다. 하지만 백엔드 개발자로서 더 자주 접하게 되는 것은 **'스키마 변경 관리'**로서의 마이그레이션입니다.

#### 의미 1: 데이터 환경의 이동 (이사 가기)

말 그대로 서식지를 옮기는 것입니다.

- **On-premise → Cloud:** 회사 전산실 서버에 있던 데이터를 AWS RDS로 옮길 때.
- **Oracle → MySQL:** 사용하는 데이터베이스 시스템 자체를 바꿀 때.
- 이때는 데이터를 안전하게 추출(Extract), 변환(Transform), 적재(Load)하는 ETL 작업이 중요합니다.

#### 의미 2: 스키마 버전 관리 (개발자의 관점) ★

우리가 Git으로 소스 코드를 버전 관리하듯이, **"데이터베이스의 구조(설계도) 변경 내역을 코드로 관리하는 것"**을 말합니다.

Prisma, TypeORM, Sequelize 같은 ORM을 사용할 때 주로 경험하게 됩니다.

**왜 마이그레이션을 해야 할까요?**

1. **협업의 일관성 (Sync):**
   - 팀원 A가 User 테이블에 nickname 컬럼을 추가했습니다.
   - 마이그레이션 파일이 없다면, 팀원 B는 코드를 실행하다가 "nickname 컬럼이 없습니다"라는 에러를 만나고 수동으로 DB를 고쳐야 합니다.
   - 마이그레이션을 쓰면 migrate 명령어 한 번으로 팀원 A와 B의 DB 구조가 똑같아집니다.
2. **안전한 배포:**
   - 개발 서버(Dev)에서 테스트한 DB 구조 변경 사항을 운영 서버(Prod)에도 실수 없이 똑같이 적용할 수 있습니다.
3. **히스토리 추적 및 롤백:**
   - "저번 주에 테이블 구조를 어떻게 바꿨지?"를 마이그레이션 파일을 통해 확인할 수 있습니다.
   - 문제가 생기면 이전 버전으로 DB 구조를 되돌리는(Revert/Rollback) 것도 가능합니다.

**예시 (Prisma)**

```
# 1. 스키마 파일(schema.prisma) 수정
# 2. 마이그레이션 생성 및 적용
npx prisma migrate dev --name add_profile_image
```

이 명령어를 치면 SQL 파일이 생성되고, DB에 profile\_image 컬럼이 추가되는 과정이 바로 마이그레이션입니다.

---

### 마치며

- **무결성(Integrity)**은 데이터가 썩지 않게 막아주는 **방부제**이자 **규칙**입니다.
- **마이그레이션(Migration)**은 데이터베이스 구조의 변화를 기록하는 **역사책**이자 **버전 관리 시스템**입니다.

이 두 가지 개념을 확실히 잡고 있다면, 단순히 "돌아가는 DB"가 아니라 "신뢰할 수 있고 관리가 용이한 DB"를 설계하는 백엔드 개발자로 성장할 수 있을 것입니다
