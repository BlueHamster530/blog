![](/blog/images/tistory-78/img1.jpg)

안녕하세요! 오늘도 코드로 세상을 구축하고, 글로 지식을 연결하는 개발자입니다. 🚀

백엔드 개발자 면접을 준비하다 보면 반드시 마주치는 거대한 산이 하나 있습니다. 바로 **데이터베이스(DB)와 ORM**이죠. 처음엔 "그냥 데이터 저장하는 곳 아냐?"라고 생각할 수 있지만, 면접관님들이 매의 눈으로 물어보는 지점은 따로 있습니다.

오늘은 우리가 왜 RDB를 믿고 쓰는지, 그리고 수많은 ORM 중에서도 왜 하필 **Prisma**에 열광하는지, 아주 쉽고 찰지게 파헤쳐 보겠습니다. 면접 전 이 글 하나면 방어력 100% 충전 완료입니다! 🛡️

### 1. RDB의 든든한 문지기: 무결성 (Integrity) 👮‍♂️

데이터베이스에서 가장 중요한 것은 무엇일까요? 속도? 용량? 아니요, 바로 '신뢰'입니다. 내가 넣은 데이터가 엉뚱하게 변하지 않고 정확해야 한다는 뜻이죠. 이것을 우아한 말로 데이터 무결성(Data Integrity)이라고 부릅니다.

쉽게 비유해 볼까요? 여러분이 인기 있는 투표 사이트를 만들었다고 가정해 봅시다. 그런데, **가입하지도 않은 유령 회원(존재하지 않는 유저)이 투표를 한다면?** 시스템은 난장판이 될 겁니다.

RDB는 이런 끔찍한 사태를 막기 위해 외래 키(Foreign Key)라는 강력한 문지기를 세워둡니다.

> "어허! 투표(Vote) 테이블에 데이터를 넣으려면, 반드시 유저(User) 테이블에 존재하는 정상적인 회원이어야만 해! 명단에 없으면 돌아가!"

이렇게 RDB는 데이터 간의 관계를 엄격하게 통제하여 데이터의 '정확성'과 '일관성'을 지켜냅니다.

---

### 2. 모 아니면 도! 심장이 쫄깃한 '트랜잭션(Transaction)' 🎲

무결성만큼이나 중요한 개념이 바로 **트랜잭션**입니다. 트랜잭션은 여러 개의 DB 작업을 '하나의 묶음(All or Nothing)'으로 처리하는 기능입니다.

다시 투표 사이트 예시로 돌아가 봅시다. 유저가 '찬성' 버튼을 눌렀을 때, 내부적으로는 2가지 일이 연속으로 일어납니다.

1. **유저 정보 업데이트:** A 유저가 '투표 완료' 상태로 변경됨.
2. **게시글 정보 업데이트:** 해당 투표 게시글의 총 찬성 카운트가 +1 증가함.

그런데 만약, 1번 작업은 성공했는데 2번 작업을 하려는 찰나에 **서버가 펑! 터져버린다면?** 💥 유저는 투표를 했다고 나오는데, 게시글의 총 투표수는 그대로인 '데이터 불일치'가 발생합니다.

이때 트랜잭션이 구원투수로 등장합니다!

```
sequenceDiagram
    participant App as Application
    participant DB as Database
    
    App->>DB: BEGIN (트랜잭션 시작)
    DB-->>App: OK
    
    App->>DB: 1. 유저 '투표 완료' 업데이트
    DB-->>App: Success
    
    App->>DB: 2. 게시글 '총 카운트 +1' 업데이트
    alt 작업 성공 시
        App->>DB: COMMIT (저장!)
        DB-->>App: 완벽하게 반영됨
    else 작업 실패/서버 다운 시
        App->>DB: ROLLBACK (모두 취소!)
        DB-->>App: 1번 작업도 없던 일로 되돌림
    end
```

트랜잭션은 "전부 성공(Commit)하거나, 하나라도 실패하면 싹 다 없던 일로 되돌려라(Rollback)!"라는 원칙을 지킵니다. 덕분에 개발자는 안심하고 복잡한 비즈니스 로직을 구현할 수 있죠.

---

### 3. 쿼리 깎는 장인은 그만! ORM과 Prisma의 이점 🪄

자, RDB가 훌륭하다는 건 알았습니다. 그런데 DB에 명령을 내리려면 복잡한 SQL 쿼리문(SELECT \* FROM...)을 텍스트로 줄줄이 써야 합니다. 오타 하나만 나도 에러가 뿜어져 나오죠.

이때 등장하는 빛과 소금이 바로 ORM (Object-Relational Mapping)입니다. 단어 그대로 객체(Object)와 관계형 DB(Relational)를 매핑해 주는 도구입니다. 복잡한 SQL 대신, 우리가 친숙한 JavaScript나 TypeScript의 객체와 메서드를 이용해 DB를 조작할 수 있게 해줍니다.

```
// 😭 쌩 SQL을 쓸 때 (오타 나기 딱 좋음)
db.query("UPDATE users SET vote_status = true WHERE id = 1");

// 🤩 ORM을 쓸 때 (직관적이고 아름다움)
prisma.user.update({
  where: { id: 1 },
  data: { voteStatus: true }
});
```

#### 💡 그중에서도 왜 'Prisma' 인가요? (feat. 타입 안정성)

수많은 ORM 중에서 Prisma가 백엔드 개발자들의 사랑을 독차지하는 이유는 단 하나, **'압도적인 타입 안정성(Type Safety)'** 때문입니다.

Prisma에 DB 스키마를 쓱싹쓱싹 적어주면, Prisma가 알아서 TypeScript 타입을 완벽하게 생성해 줍니다. 이게 왜 중요하냐고요? 개발자가 오타를 내거나 잘못된 타입의 데이터를 넣으려고 하면, **코드를 실행하기도 전에 에디터(VSCode 등)에서 빨간 줄을 쫙! 그어버리기 때문입니다.**

과거 바닐라 JS로 개발할 때는 런타임에 에러가 터져야 "아차!" 싶었지만, TS와 Prisma의 조합은 런타임 에러를 사전에 차단하는 강력한 방패가 되어줍니다. 면접관님께 "Prisma의 내장 타입을 활용해 데이터 정규화와 타입 안정성을 모두 잡았습니다"라고 어필한다면, 분명 만족스러운 미소를 보실 수 있을 겁니다. 😎

---

### 🎯 마무리하며

**무결성**으로 데이터의 신뢰를 지키고, **트랜잭션**으로 작업의 안전성을 보장하며, ORM(Prisma)으로 개발의 생산성과 타입 안정성까지 챙기는 과정. 이것이 바로 백엔드 개발자가 시스템을 견고하게 설계해 나가는 즐거움 아닐까요?

이 글이 기술 면접을 준비하시거나, 백엔드의 기본기를 다지는 모든 주니어 개발자분들께 작은 이정표가 되길 바랍니다. 모두 파이팅입니다! 🔥
