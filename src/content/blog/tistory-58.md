안녕하세요.

RESTful API를 설계하거나 공부하다 보면 반드시 마주치는 용어가 있습니다. 바로 **Stateless(무상태성)**입니다.

"서버가 상태를 저장하지 않는다"라는 문장 자체는 이해하기 쉽지만, 이것이 구체적으로 어떤 의미인지, 그리고 왜 이렇게 설계해야 하는지 깊게 파고들면 헷갈리는 경우가 많습니다.

오늘은 REST 아키텍처의 핵심 조건인 무상태성의 개념과 장단점, 그리고 이를 통해 얻을 수 있는 이점에 대해 알아보겠습니다.

### 1. 무상태성(Stateless)의 정의

무상태성이란 서버가 클라이언트의 이전 요청이나 상태(Context)를 기억하지 않는 것을 의미합니다.

즉, 클라이언트가 보내는 **각각의 요청은 서로 독립적**이어야 하며, 서버가 요청을 처리하는 데 필요한 **모든 정보를 포함**하고 있어야 합니다. 서버는 이 요청이 첫 번째 요청인지, 100번째 요청인지 관심을 두지 않으며, 오직 들어온 요청 그 자체만 보고 처리합니다.

### 2. 비유로 이해하기: 단골 카페 vs 자판기

이 개념을 우리가 실생활에서 접하는 상황에 비유해 보겠습니다.

#### Stateful (상태 유지) - 단골 카페

- **손님:** "평소 먹던 걸로 주세요."
- **직원:** (손님의 얼굴을 기억하며) "네, 아이스 아메리카노 샷 추가 맞으시죠? 여기 있습니다."

직원(서버)이 손님(클라이언트)의 정보(상태)를 기억하고 있어야 주문이 성립됩니다. 만약 직원이 바뀌면 "평소 먹던 거"가 무엇인지 모르기 때문에 주문을 처리할 수 없습니다.

#### Stateless (무상태) - 자판기

- **손님:** (버튼을 누르며) "아이스 아메리카노, 샷 추가, 결제 카드 정보 입력."
- **자판기:** "네, 처리되었습니다."

자판기(서버)는 손님이 누구인지, 어제 무엇을 마셨는지 전혀 기억하지 않습니다. 손님은 매번 자신이 원하는 메뉴와 결제 정보를 **완전하게** 입력해야 합니다. 대신 자판기 기계가 바뀌어도(서버 교체), 손님은 똑같이 주문 정보를 입력하면 문제없이 커피를 마실 수 있습니다.

### 3. 기술적 차이점

#### Stateful (기존 세션 방식)

서버는 클라이언트의 로그인 정보나 상태를 서버 메모리(세션)에 저장합니다. 클라이언트는 세션 ID만 보내면 서버가 자신의 메모리를 뒤져서 "아, 철수구나"라고 인식합니다.

- **문제점:** 서버가 여러 대일 경우, A 서버에 로그인 정보를 저장했는데 다음 요청이 B 서버로 가면 B 서버는 철수를 모릅니다. 이를 해결하기 위해 세션 클러스터링 같은 복잡한 기술이 필요합니다.

#### Stateless (REST API 방식)

서버는 아무것도 저장하지 않습니다. 클라이언트는 요청을 보낼 때마다 토큰(JWT 등)에 내 정보(나는 철수고, 권한은 관리자야)를 꽉 채워서 보냅니다. 서버는 이 토큰이 위조되지 않았는지만 검증하고 바로 로직을 수행합니다.

- **장점:** 요청 자체에 모든 정보가 있으므로, 요청이 A 서버로 가든 B 서버로 가든 상관없이 똑같이 처리할 수 있습니다.

### 4. 왜 무상태(Stateless)로 만들어야 할까?

가장 큰 이유는 **확장성(Scalability)** 때문입니다.

서비스 사용자가 갑자기 늘어나서 서버를 1대에서 100대로 늘려야 한다고 가정해 봅시다(Scale-out).

- **Stateful:** 서버를 늘릴 때마다 각 서버 간에 세션 정보를 동기화해야 하는 엄청난 비용이 발생합니다.
- **Stateless:** 서버를 무한정 늘려도 상관없습니다. 어차피 서버는 상태를 저장하지 않고, 들어오는 요청만 처리하면 되기 때문입니다. 클라우드 환경이나 마이크로서비스 아키텍처(MSA)에서 REST API가 표준처럼 쓰이는 이유가 바로 이 확장성 덕분입니다.

### 5. 단점과 트레이드오프

물론 단점도 있습니다.

서버가 기억을 하지 않기 때문에, 클라이언트는 매 요청마다 인증 정보(헤더)나 상태 정보를 포함해서 보내야 합니다. 이로 인해 **데이터 전송량(패킷의 크기)이 늘어나는 오버헤드**가 발생할 수 있습니다.

하지만 현대의 네트워크 환경에서는 이러한 약간의 데이터 증가보다 서버 확장성을 확보하는 것이 훨씬 더 큰 이득이기 때문에 무상태 설계를 지향합니다.

### 마치며

정리하자면 다음과 같습니다.

1. **Stateless:** 서버는 클라이언트의 상태를 기억하지 않는다.
2. **조건:** 모든 요청은 그 자체로 완결적이어야 한다(필요한 모든 정보를 담아야 한다).
3. **목적:** 서버의 확장성(Scale-out)을 극대화하기 위해서다.

REST API를 설계할 때 "이 정보를 세션에 저장할까?"라는 고민이 든다면, "이 요청만으로 서버가 처리가 가능한가?"를 먼저 떠올려 보시길 바랍니다.
