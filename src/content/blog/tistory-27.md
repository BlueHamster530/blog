안녕하세요!

우리가 웹사이트를 보거나 앱을 사용할 때, '데이터를 불러오는 중...'이라는 메시지를 흔히 봅니다. 이 과정은 클라이언트(브라우저, 앱)가 서버(데이터가 있는 컴퓨터)에게 **필요한 정보 좀 주세요!**\*\*라고 요청(Request)하고, 서버가 **여기 있습니다!**라고 응답(Response)하는 통신 과정입니다.

이 **요청**과 **응답**은 웹 개발의 가장 기본이 되는 뼈대입니다.

오늘은 이 요청과 응답이 어떻게 구성되는지, 특히 사용자가 원하는 데이터를 정확히 전달하는 **다양한 인자 전달 방법**(쿼리, 파라미터 등)과 서버의 처리 상태를 알려주는 **응답 코드**에 대해 자세히 알아보겠습니다.

---

### 1. 요청(Request)과 응답(Response)이란?

가장 간단한 예시로 시작하겠습니다.

- **요청 (Request):** 클라이언트가 서버로 필요한 것을 **요청**하는 행동입니다.
  - 예: <https://api.maplescouter.com/api/id?name=아델&preset=00000>®ion=kms
  - 위 링크는 api.maplescouter.com 서버의 /api/id 주소로 3가지 정보(name, preset, region)를 담아 **"이 조건에 맞는 ID를 알려주세요"**라고 요청한 것입니다.
- **응답 (Response):** 서버가 요청을 처리한 뒤 클라이언트에게 **결과**를 돌려주는 행동입니다.
  - 예: (응답 코드: 201 Created) + (응답 Body: { "캐릭터 정보 JSON..." })
  - 서버는 "요청하신 조건으로 새 정보를 성공적으로 생성(201)했습니다. 여기(Body)에 요청한 캐릭터 정보가 있습니다"라고 응답합니다.

---

### 2. 서버에게 '무엇을' 원하는지 말하는 방법 (인자 전달)

서버에 데이터를 요청할 때, "그냥 데이터 주세요"가 아니라 "A의 B 정보를 주세요"처럼 구체적인 조건을 전달해야 합니다. 이 '조건(인자)'을 전달하는 방법은 여러 가지가 있으며, 각기 다른 용도로 사용됩니다.

#### 1. 쿼리 스트링 (Query String)

URL 주소 뒤에 ?를 붙여 **'key=value'** 형태로 데이터를 전달하는 방식입니다. & 기호로 여러 개의 쿼리를 연결할 수 있습니다.

- **예시:** <https://maplescouter.com/info?name=아델&preset=00000>
- **의미:** maplescouter.com 웹사이트에 **"아델"**이라는 **name**과 **00000**번 **preset** 정보를 기준으로 정보를 보여달라는 요청입니다.
- **주요 용도:** 사용자가 원하는 \*\*특정 정보(검색, 필터링, 정렬)\*\*를 서버로부터 가져오기 위한 **'요청서'** 역할을 합니다.

#### 2. 경로 매개변수 (Path Parameters)

URL 경로의 일부를 변수처럼 사용하여 값을 전달합니다. 보통 특정 게시물, 사용자, 상품 등 **고유한 자원**을 명확하게 지정할 때 사용합니다.

- **예시:** fetch('/posts/123'); 또는 bluehamster.tistory.com/28
- **의미:** "28번째 게시물", "123번 게시물"을 보여달라는 의미입니다.
- **장점:** URL이 의미적으로 명확하고 깔끔합니다.
- **단점:** 여러 개의 복잡한 검색 조건이나 선택적인 값을 전달하기엔 부적합합니다.

#### 3. 요청 본문 (Request Body)

HTTP 요청의 **본문(Body)**에 데이터를 담아 보내는 방식입니다. URL과 달리 데이터가 눈에 보이지 않는 곳에 실리기 때문에, **크기가 크거나 복잡하거나 민감한 데이터**를 전송할 때 주로 사용됩니다.

- **HTTP 메소드:** GET 요청에서는 사용할 수 없고, 주로 **POST, PUT, PATCH** 등과 함께 사용됩니다.
- **주요 용도:**
  - 회원 가입, 로그인 등 **민감한 정보(비밀번호 등)**를 전송할 때
  - 게시글 작성, 상품 등록 등 **새로운 데이터를 생성**할 때
  - **복잡한 구조의 데이터(JSON)**나 대용량 데이터를 보낼 때
- **장점:** URL에 데이터가 노출되지 않아 보안에 유리하며, 전송 데이터 길이에 제한이 없습니다. JSON 같은 구조적 데이터를 보내기 용이합니다.
- **단점:** GET 요청에서 사용할 수 없으며, 브라우저 주소창에 직접 입력하는 방식으로는 요청할 수 없습니다.

#### 4. HTTP 헤더 (HTTP Headers)

HTTP 요청의 **헤더**에 값을 넣어 보내는 방식입니다. 주로 데이터 자체가 아닌, 요청에 대한 \*\*부가 정보(메타데이터)\*\*를 전달할 때 사용됩니다.

- **주요 용도:**
  - **인증 정보 (Authentication):** API 키, JWT(JSON Web Token) 등을 Authorization 헤더에 담아 전달할 때
  - **클라이언트 상태 정보:** 요청하는 콘텐츠의 형식(Content-Type), 언어(Accept-Language) 등을 전달할 때
- **장점:** 요청의 URL이나 Body를 건드리지 않고 부가 정보를 깔끔하게 전달할 수 있습니다.
- **단점:** 전달하려는 주된 데이터를 담는 용도로는 부적합합니다.

### 3. 서버의 대답을 해석하는 법: 응답 코드 (Status Code)

서버는 응답을 줄 때, 요청이 성공했는지, 실패했다면 왜 실패했는지 알려주는 **세 자리 숫자 코드**를 함께 보냅니다. (앞서 본 201처럼 말이죠.)

이 코드는 백 단위 숫자별로 큰 의미가 나뉩니다.

- **1xx (정보 제공):** 임시 응답입니다. "요청은 받았고 처리 중이니 계속 진행하세요."
- **2xx (성공):** 클라이언트의 요청이 서버에서 **성공적으로 처리**되었음을 의미합니다. (예: 200 OK, 201 Created)
- **3xx (리다이렉션):** 완전한 처리를 위해 추가 동작이 필요합니다. "요청한 주소가 바뀌었으니 그 주소로 다시 시도하세요."
- **4xx (클라이언트 에러):** 클라이언트의 **요청 메시지 내용이 잘못된 경우**입니다. (예: 404 Not Found - 요청한 주소가 없음, 401 Unauthorized - 인증 안 됨)
- **5xx (서버 에러):** **서버 문제**로 메시지 처리에 문제가 발생한 경우입니다. (예: 500 Internal Server Error - 서버 내부 오류)

(자세한 코드 종류는 [이전 포스팅](https://www.google.com/search?q=https://bluehamster.tistory.com/28)을 참고 부탁드립니다.)

### 4. (고급) 더 나은 응답(Response Body) 구조 고민하기

서버가 데이터를 성공적으로 돌려주기만 하면 끝일까요? 클라이언트가 **'사용하기 편하게'** 데이터를 구조화하여 보내주는 것도 매우 중요합니다.

예를 들어, 앞선 예시에서 이런 응답 Body를 받았다고 가정해 봅시다.

```
{
  "calculatedDamage_300": 150000,
  "calculatedDamage_380": 145000,
  "character_name": "아델",
  ...
}
```

calculatedDamage 값이 \_300, \_380처럼 키 이름에 붙어있습니다. 당장은 쓸 수 있지만, 만약 400, 420 레벨이 추가되면 calculatedDamage\_400, calculatedDamage\_420 키가 계속 늘어날 것입니다. 클라이언트는 이 키들을 일일이 확인해야 해서 불편합니다.

#### 개선 방안

이 응답 구조를 다음과 같이 **그룹화**하여 개선할 수 있습니다.

**개선안 1: 데이터 중첩**

JSON

```
{
  "calculatedDamage": {
    "300": 150000,
    "380": 145000
  },
  "character_name": "아델",
  ...
}
```

**개선안 2: 그룹으로 묶기**

JSON

```
{
  "info300": {
    "calculatedDamage": 150000,
    ...
  },
  "info380": {
    "calculatedDamage": 145000,
    ...
  },
  "character_name": "아델"
}
```

이전 게임 개발이나 웹 콘텐츠 개발 시에도 그룹별로 묶어서 작성하는 방법을 선호했듯이, 이렇게 데이터를 종류별로 묶어주면 클라이언트(코드를 작성하는 다른 개발자)가 300 그룹과 380 그룹을 구분하기 훨씬 용이해집니다.

---

### 마치며

오늘은 클라이언트와 서버가 대화하는 방식인 **요청(Request)**과 **응답(Response)**의 기본 구조에 대해 알아보았습니다.

어떤 방식으로 데이터를 요청(쿼리, 파라미터, 바디)하는 것이 효율적일지, 그리고 서버는 어떤 상태 코드와 구조화된 데이터로 응답해야 클라이언트가 사용하기 편할지 고민하는 것은 **좋은 API 설계의 첫걸음**입니다.
