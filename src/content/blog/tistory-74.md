안녕하세요!

'코드로 세상을 구축하고 글로 지식을 연결하는' 여러분의 동네 엔지니어입니다. 👨‍💻✨

지난번 포스팅(이라 쓰고 우리의 상상 속 기억이라 읽습니다)에서 우리는 Node.js의 싱글 스레드 한계를 극복하기 위해\*PM2 클러스터링(Clustering)이라는 마법을 부렸습니다. 요리사(프로세스)를 4명으로 복제해서 서버의 성능을 영혼까지 끌어올렸죠.

그런데 기쁨도 잠시, 새로운 요구사항이 들어왔습니다.

> 🗣️ 기획자: "개발자님! 매일 밤 12시에 휴면 회원들에게 안내 메일을 보내는 기능을 추가해 주세요!"

아하! 주기적인 작업이군요? 가벼운 마음으로 자바스크립트의 영원한 친구 setInterval이나 국민 스케줄러 node-cron을 도입하려고 하셨나요? **잠깐 멈추세요! 지금 그대로 배포했다간 내일 아침 고객센터 전화기에 불이 날 겁니다.** 🔥

## 🚨 문제의 발단: "요리사가 4명이면 알람도 4번 울린다"

PM2 클러스터 모드로 앱을 실행하면, 똑같은 소스 코드를 가진 프로세스가 CPU 코어 수만큼 띄워집니다. 만약 프로세스가 4개 떠 있는 상태에서 단순하게 node-cron으로 매일 밤 12시에 메일을 보내라고 스케줄링을 걸어두면 어떻게 될까요?

**12시 정각이 되는 순간, 4개의 프로세스가 동시에 알람을 듣고 똑같은 유저에게 4번의 메일을 발송해 버립니다.**

비유하자면, 주방에 4명의 요리사가 있는데 벽에 걸린 알람시계가 울리자 4명 모두 똑같은 요리를 만들기 시작하는 꼴입니다. 재료 낭비, 시간 낭비, 그리고 손님(유저)의 분노를 유발하게 되죠. setInterval은 말할 것도 없고, 단순히 시간만 제어해 주는 node-cron도 이 '다중 프로세스 환경'의 근본적인 문제는 해결해주지 못합니다.

---

## 💡 해결책: "중앙 주문서(Redis)와 작업반장(Bull)의 도입"

이 문제를 해결하려면 4명의 요리사가 **"공통된 하나의 주문서"**를 보고, **"누군가 하나가 그 주문을 잡으면 다른 사람은 건드리지 않게"** 만들어야 합니다.

이때 등장하는 구세주가 바로 인메모리 데이터베이스인 **Redis**와 이를 활용한 메시지 큐 라이브러리 **Bull**입니다.

### 📊 분산 환경에서의 스케줄링 아키텍처 (Mermaid)

```
graph TD
    Cron[스케줄러: 밤 12시 트리거] -->|작업 생성| Redis[(Redis Queue)]
    
    subgraph PM2 Cluster [PM2 클러스터 (Express)]
        W1(Worker 1)
        W2(Worker 2)
        W3(Worker 3)
        W4(Worker 4)
    end

    Redis -.->|작업 가져감| W2
    Redis x--x|이미 가져감| W1
    Redis x--x|이미 가져감| W3
    Redis x--x|이미 가져감| W4
    
    W2 --> Mail[이메일 1회 정상 발송 ✉️]
```

구조는 이렇습니다.

1. 밤 12시가 되면 특정 스케줄러가 **"메일 보내기"라는 티켓을 Redis 큐에 1장만** 넣습니다.
2. PM2로 띄워진 4개의 워커(요리사)들이 Redis를 바라보고 있다가, **가장 손이 빠른 워커 하나가 그 티켓을 낚아챕니다.**
3. 티켓은 이미 사라졌으므로 나머지 3개의 워커는 아무 일도 하지 않고 본업(API 응답)에 충실합니다.

## 🛠️ 코드로 살펴볼까요? (Bull 도입하기)

Bull 라이브러리를 사용하면 이 복잡해 보이는 과정을 아주 우아하게 처리할 수 있습니다. (Redis 서버가 미리 설치되어 실행 중이어야 합니다!)

```
$ npm install bull
```

```
// queue.js (작업 큐 설정 파일)
const Queue = require('bull');

// 'mailQueue'라는 이름의 작업 큐 생성 (Redis에 연결)
const mailQueue = new Queue('mailQueue', 'redis://127.0.0.1:6379');

// 워커(요리사)들이 해야 할 행동 정의
mailQueue.process(async (job, done) => {
  console.log(`[프로세스 ${process.pid}] 가 작업을 잡았습니다! 유저 ID: ${job.data.userId}`);
  
  // 가상의 메일 발송 로직
  await sendEmail(job.data.userId);
  
  done(); // 작업 완료 보고
});

module.exports = mailQueue;
```

이제 작업을 스케줄링해 볼까요? Bull에는 자체적으로 Cron 문법을 지원하는 repeat 옵션이 있습니다.

```
// app.js (Express 메인 서버)
const express = require('express');
const mailQueue = require('./queue');
const app = express();

// 서버가 시작될 때 스케줄 작업을 큐에 등록 (단, 중복 생성 방지 옵션 필수!)
mailQueue.add(
  { userId: 'all-dormant-users' }, // 작업 데이터
  { 
    repeat: { cron: '0 0 * * *' }, // 매일 자정에 실행 (Cron 문법)
    jobId: 'daily-mail-job' // 고유 ID를 부여하여 PM2 워커들이 여러 번 add해도 큐에는 1개만 등록됨! (핵심)
  }
);

app.listen(3000, () => {
  console.log(`Express 서버 실행 완료 (PID: ${process.pid})`);
});
```

여기서 가장 중요한 핵심은 jobId를 명시하는 것입니다. PM2로 서버가 4개 동시에 켜지면서 mailQueue.add를 4번 호출하겠지만, jobId가 같기 때문에 똑똑한 Redis와 Bull은 큐에 중복해서 작업을 쌓지 않습니다. 완벽하죠!

## ✨ 마무리하며: 성장을 위한 근육통

처음 로컬에서 개발할 때 setInterval로 잘만 돌아가던 코드가, 실제 운영(Production) 환경에서 PM2를 만나고 스케일 아웃(Scale-out) 되면서 예상치 못한 이슈들을 만들어냅니다.

하지만 이런 문제를 겪고, "왜 그럴까?" 고민하고, "Redis와 메시지 큐"라는 새로운 무기를 장착하여 해결해 나가는 과정 자체가 주니어에서 미들급 엔지니어로 성장하는 훌륭한 근육통이라고 생각합니다. 코드로 세상을 구축하는 우리의 여정은 늘 이렇게 흥미진진하니까요!

## 📝 회고 (KPT)

- **Keep (유지할 점):**
  - 단순한 기능 구현(setInterval)에 그치지 않고, 다중 프로세스(PM2)라는 현재의 시스템 아키텍처 상황을 고려하여 발생할 수 있는 사이드 이펙트(작업 중복 실행)를 사전에 인지한 점.
  - 문제를 해결하기 위해 Redis와 Bull 기반의 메시지 큐 아키텍처를 도입하여 시스템의 안정성을 높인 점.
- **Problem (문제점):**
  - 초반 아키텍처 설계 시 단일 서버 환경만 고려하여 스케줄러를 구상했었음. 분산 환경에서는 상태(State)와 스케줄링이 어떻게 공유되어야 하는지에 대한 이해가 부족했음.
- **Try (시도할 점):**
  - Bull의 업그레이드 버전이자 속도가 훨씬 빠른 BullMQ 라이브러리로의 마이그레이션 검토해 보기.
  - 실패한 작업(Failed Jobs)을 재시도(Retry)하거나 슬랙(Slack) 알림으로 모니터링할 수 있는 파이프라인 추가 구축하기.
