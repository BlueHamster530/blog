안녕하세요!

오늘도 여러분의 삽질 시간을 줄여드리기 위해 키보드를 잡은 개발자입니다. 👨‍💻

여러분, 혹시 새벽에 운영 DB에 접속해서 쿼리를 날려본 적 있으신가요? 오늘 소개할 이야기는 유튜브 채널 '코딩하는기술사'님의 20년 전 흑역사에서 가져온, 아주 무시무시하고도 뼈아픈 교훈입니다. 바로 "**WHERE 절 없는 UPDATE 쿼리 한 방으로 전체 게임 유저를 튕겨낸 사건"**입니다.

![](/blog/images/tistory-73/img1.png)

*"설마 나도 저런 실수를 할까?"* 싶으시죠? 하지만 방심은 금물! 이 사건을 통해 DB의 **락(Lock)** 메커니즘을 제대로 파악해 봅시다.

## 🚨 사건의 발단: "나.. 때문인가?"

사건은 약 20년 전 평화로운 근무 시간에 발생했습니다. 회원 관련 테이블에 데이터 업데이트가 필요했던 기술사님은 별생각 없이 운영 중인 DB에 아래와 같은 쿼리를 날렸습니다.

```
-- 등줄기에 땀을 흐르게 한 바로 그 쿼리 (예시)
UPDATE user_info 
SET status = 'ACTIVE'; 
-- ... WHERE 절은 어디에...? 😱
```

쿼리를 실행한 지 얼마 지나지 않아 모니터링 시스템에서 경고음이 미친 듯이 울리기 시작했습니다. DB 응답 시간이 급증하고, 커넥션 오류가 폭증하더니, 결국 **모든 게임 유저의 접속이 끊기고 말았습니다.** (회사 안이 웅성웅성해지는 건 덤이죠...)

대체 왜 이런 일이 발생한 걸까요?

## 🔍 원인 분석: 락(Lock)과 풀 스캔(Full Scan)의 환장할 콜라보

### 1. Row Lock vs Table Lock (비유로 이해하기)

이 사태를 이해하려면 데이터베이스의 **락(Lock)** 개념을 알아야 합니다.

- **Row Lock (행 잠금):** 영화관에서 내가 예매한 **'지정석'**만 찜하는 겁니다. 내가 A1 자리를 예매 중이어도, 다른 사람은 B2 자리를 예매(접근)할 수 있습니다. 정상적인 시스템이죠.
- **Table Lock (테이블 잠금):** 내가 영화관을 **'통대관'** 해버린 겁니다. 내가 볼일(트랜잭션)을 다 끝낼 때까지 아무도 영화관(테이블)에 들어올 수 없습니다.

### 2. WHERE 절이 없으면 무슨 일이?

일반적으로 WHERE 절을 사용해 특정 조건의 인덱스(Index)를 타면, DB는 똑똑하게 해당 행(Row)만 잠급니다(Row Lock). 다른 데이터들은 정상적으로 읽고 쓰기가 가능하죠.

하지만 **WHERE 절이 없거나 인덱스를 타지 못하면?** DB는 업데이트할 데이터를 찾기 위해 테이블의 첫 번째 행부터 끝까지 전부 뒤지는 **풀 스캔(Full Scan)**을 시작합니다.

이때 무시무시한 일이 발생합니다. 스캔하는 모든 행에 락을 걸어버리기 때문에, 사실상 **테이블 전체에 락이 걸리는 것(Table Lock)과 동일한 효과**가 발생합니다.

```
sequenceDiagram
    participant Dev as 개발자
    participant DB as 데이터베이스
    participant App as 게임 서버 (App)
    participant User as 유저
    
    Dev->>DB: UPDATE (WHERE 절 없음)
    note over DB: 테이블 전체 Full Scan<br/>모든 행에 Lock 발생!
    User->>App: 게임 액션 (아이템 획득 등)
    App->>DB: 다른 트랜잭션 요청 (UPDATE/INSERT)
    note over DB: Lock 해제 대기 중... (Wait)
    DB--xApp: Lock 대기 타임아웃 발생!
    App--xUser: 커넥션 풀 고갈 & 세션 강제 종료 (튕김)
```

**결과적으로:**

1. 모든 행이 잠금 상태가 됨
2. 다른 유저들의 요청(트랜잭션)이 DB에 접근하지 못하고 대기(Wait)
3. DB 응답 지연 → 애플리케이션(게임 서버) 타임아웃 및 커넥션 풀 고갈
4. 게임 서버 전체 세션 강제 종료 (유저들 단체로 튕김 😭)

## 💡 해결책 및 실무 베스트 프랙티스 (미래의 나를 위한 기록)

이 사건 이후, 우리는 다음과 같은 철칙을 세워야 합니다

1. **운영 DB 직접 접근 지양:** 운영 DB에 손으로 직접 쿼리를 치는 행위는 최대한 피해야 합니다.
2. **SELECT로 영향 범위 선 파악:** UPDATE나 DELETE 전에는 반드시 SELECT 문으로 내가 조작할 데이터가 몇 건인지, 정확한지 확인합니다.
3. **실행 계획(EXPLAIN) 확인 습관:** 쿼리를 실행하기 전, 인덱스를 제대로 타는지 실행 계획을 확인합니다.
4. **대량 업데이트는 나눠서 처리:** 한 번에 수만/수십만 건을 업데이트하면 락이 길어집니다. LIMIT를 걸거나 배치(Batch) 작업으로 쪼개서 실행하세요.
5. **트랜잭션은 최대한 짧게!:** DB 락 대기 시간을 최소화하기 위해 트랜잭션 길이를 짧게 유지합니다.
