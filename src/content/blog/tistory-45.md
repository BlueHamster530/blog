안녕하세요.

웹이나 앱 서비스를 개발하다 보면 프로필 사진 변경, 게시글 이미지 첨부 등 파일 업로드를 구현해야 하는 순간이 반드시 찾아옵니다.

텍스트 데이터(JSON)만 주고받을 때는 단순했던 통신이, 파일이라는 바이너리 데이터가 끼어들면 고려해야 할 점이 많아집니다.

파일을 서버로 어떻게 전송할지, 그리고 전송받은 파일을 어디에 저장할지에 따라 시스템의 성능과 비용이 크게 달라지기 때문입니다.

오늘은 백엔드 서버에서 이미지를 업로드하는 대표적인 전송 방식들과 저장 전략에 대해 알아보겠습니다.

### 1. 전송 방식: 클라이언트에서 서버로

이미지를 클라이언트(프론트엔드)에서 서버(백엔드)로 보내는 방법은 크게 세 가지가 있습니다.

#### 1) Multipart/form-data 방식

가장 표준적이고 전통적인 파일 전송 방식입니다.

HTML의 Form 태그에서 파일을 전송할 때 사용하던 방식이며, HTTP 요청 바디를 여러 개의 파트(Part)로 쪼개서 전송합니다. 각 파트에는 텍스트 데이터와 바이너리 파일 데이터가 섞여 들어갈 수 있습니다.

장점: 바이너리 데이터를 변환 없이 그대로 전송하므로 전송 효율이 가장 좋습니다. 대용량 파일 전송에 적합합니다. 단점: 서버 쪽에서 이 데이터를 파싱(해석)하기 위한 별도의 처리가 필요합니다. (Node.js의 Multer, Java의 MultipartFile 등이 이 역할을 합니다.)

#### 2) Base64 인코딩 방식

이미지 파일(바이너리)을 긴 문자열(텍스트)로 변환하여 전송하는 방식입니다.

이미지를 텍스트로 바꾸기 때문에, 별도의 설정 없이 우리가 흔히 쓰는 JSON 데이터 안에 포함시켜서 보낼 수 있습니다.

장점: 구현이 매우 간단합니다. 이미지도 일반 텍스트 데이터처럼 취급할 수 있어 HTTP 요청을 단순화할 수 있습니다. 단점: 인코딩 과정에서 데이터 크기가 원본 대비 약 33% 커집니다. 따라서 트래픽 비용이 증가하고, 인코딩/디코딩 과정에서 CPU 연산 비용이 발생하므로 대용량 파일에는 부적합합니다.

#### 3) Presigned URL (서명된 URL) 방식

최근 대규모 서비스에서 가장 많이 사용하는 방식입니다. 클라이언트가 이미지를 백엔드 서버로 직접 보내는 것이 아니라, AWS S3 같은 클라우드 저장소로 직접 업로드하는 방식입니다.

1. 클라이언트가 백엔드 서버에 "업로드할 주소를 주세요"라고 요청합니다.
2. 백엔드 서버는 클라우드 저장소에 접근하여 임시로 업로드 권한이 부여된 URL(Presigned URL)을 발급받아 클라이언트에게 줍니다.
3. 클라이언트는 받은 URL을 이용해 이미지를 클라우드 저장소로 직접 전송합니다.

장점: 백엔드 서버를 거치지 않으므로 서버의 CPU와 네트워크 대역폭을 아낄 수 있습니다. 서버 부하를 획기적으로 줄일 수 있습니다. 단점: 구현 로직이 다소 복잡해집니다.

### 2. 저장 방식: 서버에서 어디로?

서버가 이미지를 받았다면(혹은 관리해야 한다면) 어디에 저장해야 할까요?

#### 1) 웹 서버 로컬 디스크 (Filesystem)

서버 컴퓨터의 폴더(예: /uploads)에 파일을 직접 저장하는 방식입니다.

특징: 구현이 가장 쉽고 비용이 들지 않습니다. 문제점: 서버를 여러 대 사용하는(로드 밸런싱) 환경에서는 사용할 수 없습니다. A 서버에 저장된 이미지를 B 서버에서는 읽을 수 없기 때문입니다. 또한 서버가 죽으면 이미지도 함께 사라질 위험이 있습니다.

#### 2) 데이터베이스 내부 (BLOB)

MySQL이나 Oracle 같은 DB에 이미지 파일을 바이너리 형태(BLOB)로 직접 저장하는 방식입니다.

특징: 데이터 관리가 일원화됩니다. 문제점: 데이터베이스는 비싸고 중요한 자원입니다. 거대한 이미지 파일들이 DB 공간을 차지하면 성능이 급격히 저하되고, 백업 및 복구 시간이 엄청나게 길어집니다. 일반적으로 권장하지 않는 방식입니다.

#### 3) 오브젝트 스토리지 (Object Storage)

AWS S3, Google Cloud Storage, Azure Blob Storage 같은 외부 클라우드 저장소를 사용하는 방식입니다. 백엔드 서버는 이미지가 저장된 URL(경로)만 데이터베이스에 문자열로 저장합니다.

특징: 용량이 무제한에 가깝고 내구성이 매우 뛰어납니다. 서버가 여러 대로 늘어나도 이미지는 외부의 한곳에 있으므로 공유가 쉽습니다. 권장: 현업에서 가장 표준적으로 사용하는 방식입니다.

### 마치며

소규모 프로젝트나 학습용이라면 Multipart 방식으로 받아 로컬 디스크에 저장하는 것으로 시작해도 충분합니다.

하지만 실제 서비스를 운영한다면, 서버의 부하를 줄이고 확장성을 확보하기 위해 Presigned URL 방식을 사용하여 오브젝트 스토리지에 저장하는 구조를 강력하게 추천합니다.

이미지 업로드 방식의 선택은 서비스의 규모와 비용, 그리고 서버 아키텍처에 따라 달라져야 합니다.
