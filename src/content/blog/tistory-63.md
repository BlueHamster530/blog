안녕하세요.

Jest의 기본 문법, 비동기 처리, 그리고 Mocking까지 백엔드 테스트를 위한 기술적인 도구들은 모두 손에 쥐었습니다.

이제 여러분은 신나게 테스트 코드를 작성하기 시작합니다. 그러다 보면 문득 이런 궁금증이 생길 겁니다.

**"도대체 테스트를 얼마나 짜야 하는 거지? 모든 파일, 모든 줄을 다 테스트해야 하나?"**

오늘은 내가 작성한 테스트가 코드를 얼마나 잘 커버하고 있는지 측정하는 방법(Test Coverage)과, 수치 너머에 있는 **'진짜 좋은 테스트'**란 무엇인지에 대해 이야기해 보려 합니다.

---

### 1. 테스트 커버리지(Coverage) 측정하기

Jest는 별도의 도구 설치 없이 옵션 하나만으로 강력한 커버리지 리포트를 만들어줍니다.

터미널에서 기존 명령어 뒤에 --coverage를 붙여보세요.

```
# npm test -- --coverage 와 같습니다.
npx jest --coverage
```

이 명령어를 실행하면 테스트가 수행된 후, 터미널에 아래와 같은 표가 출력됩니다.

```
------------------|---------|----------|---------|---------|-------------------
File              | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s 
------------------|---------|----------|---------|---------|-------------------
All files         |   85.71 |       50 |     100 |   85.71 |                   
 validator.js     |     100 |      100 |     100 |     100 |                   
 userService.js   |   75.45 |       25 |     100 |   76.32 | 14-18             
------------------|---------|----------|---------|---------|-------------------
```

또한 프로젝트 루트에 coverage라는 폴더가 생성됩니다. 그 안의 lcov-report/index.html 파일을 브라우저로 열면, 어떤 코드의 몇 번째 줄이 테스트되지 않았는지 시각적으로 아주 예쁘게 확인할 수 있습니다.

---

### 2. 커버리지 지표 해석하기

리포트에 나오는 4가지 핵심 지표의 의미는 다음과 같습니다.

1. **Statements (구문):** 코드의 명령문이 적어도 한 번은 실행되었는가?
2. **Branches (분기):** if-else, switch 등의 모든 분기점을 통과했는가? (가장 중요합니다!)
3. **Functions (함수):** 정의된 함수가 적어도 한 번은 호출되었는가?
4. **Lines (라인):** 소스 코드의 라인이 실행되었는가?

특히 **Branch** 커버리지가 낮다면, 특정 조건(if (error) ...)에 대한 예외 처리가 테스트되지 않았을 확률이 높습니다.

---

### 3. 커버리지 100%의 함정

많은 개발 팀이나 관리자들이 "커버리지 80% 이상 유지" 혹은 "100% 달성"을 목표로 삼곤 합니다. 물론 높은 커버리지는 코드의 안정성을 대변하는 좋은 지표입니다.

하지만 **"커버리지 100% = 버그 없는 완벽한 코드"는 절대 아닙니다.**

간단한 예시를 들어보겠습니다.

```
// 대상 코드
function add(a, b) {
  return a + b;
}

// 테스트 코드
test('1 + 2 = 3', () => {
  expect(add(1, 2)).toBe(3);
});
```

이 테스트를 돌리면 add 함수의 모든 줄을 실행하므로 **커버리지는 100%**가 나옵니다. 하지만 만약 누군가 add(1, null)이나 add("1", 2)를 호출한다면 어떻게 될까요? 의도치 않은 결과가 나올 수 있지만, 커버리지 리포트는 이 사실을 알려주지 않습니다.

즉, 커버리지는 **"내가 작성한 테스트가 코드를 훑고 지나갔는지"**를 알려줄 뿐, **"로직이 올바른지"**를 보장해주지는 않습니다. 숫자에 집착하여 무의미한 테스트를 늘리기보다, 중요한 비즈니스 로직의 엣지 케이스(Edge Case)를 고민하는 것이 훨씬 가치 있습니다.

---

### 4. 그렇다면 '좋은 테스트'란 무엇일까요?

백엔드 개발을 공부하며 느낀, 좋은 테스트 코드가 갖춰야 할 조건들을 정리해 보았습니다.

#### ① 신뢰할 수 있어야 한다 (Deterministic)

어제는 통과하고 오늘은 실패하는 테스트는 최악입니다. (보통 날짜 관련 로직이나 외부 API 의존성 때문에 발생합니다.) 언제, 어디서, 누가 실행해도 항상 같은 결과가 나와야 합니다.

#### ② 리팩토링 내성 (Refactoring Resistance)

내부 구현 방식을 조금 바꿨다고 해서 테스트가 깨지면 안 됩니다.

- **나쁜 예:** "데이터베이스 연결 함수를 호출했는지 확인" (구현에 집착)
- **좋은 예:** "유저를 저장하면 조회가 가능한지 확인" (결과와 행동에 집중)

#### ③ 빨라야 한다

테스트가 느리면 개발자는 테스트 돌리기를 귀찮아하게 됩니다. Mocking을 적절히 활용하여 수 초 안에 피드백을 받을 수 있어야 합니다.

#### ④ 문서의 역할을 해야 한다

테스트 코드의 describe와 test 설명만 읽어도 이 기능이 무엇을 하는지, 어떤 예외 상황이 있는지 파악할 수 있어야 합니다.
