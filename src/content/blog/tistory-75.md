> 트래픽 폭주로 인한 서버 다운을 막아주는 로드밸런싱의 핵심 개념을 알아봅니다. 정적 로드밸런싱(라운드 로빈, IP 해시)과 동적 로드밸런싱(최소 연결, 최소 응답 시간)의 차이점과 작동 방식을 식당 웨이터 비유를 통해 초보자도 아주 쉽게 이해할 수 있도록 정리했습니다.

안녕하세요!

여러분이 열심히 만든 서비스가 갑자기 대박이 나서 사용자가 몰려들었다고 상상해 봅시다. 기쁨도 잠시, 서버가 트래픽을 버티지 못하고 뻗어버린다면? 끔찍하죠. 이때 우리의 서버가 죽지 않게 멱살 잡고 캐리해 주는 구원자가 바로 **로드밸런서(Load Balancer)**입니다.

로드밸런서는 들어오는 트래픽(손님)을 여러 대의 서버(웨이터)에게 골고루 나눠주는 '식당 매니저' 역할을 합니다. 그런데 이 매니저가 손님을 분배하는 방식은 크게 **정적(Static)**인 방식과 **동적(Dynamic)**인 방식으로 나뉩니다. 오늘 이 두 방식의 차이점과 대표적인 알고리즘들을 아주 쉽게 파헤쳐 보겠습니다.

---

### 1. 정적 로드밸런싱 (Static Load Balancing)

정적 방식은 매니저가 **"현재 서버의 상태는 묻지도 따지지도 않고, 정해진 규칙대로만"** 손님을 나누는 방식입니다. 웨이터가 지금 코피를 쏟고 있든, 한가하게 쉬고 있든 상관없이 매뉴얼대로만 행동합니다.

- **라운드 로빈 (Round Robin):** 가장 단순하고 공평한 방식입니다. 1번 손님은 A 서버, 2번 손님은 B 서버, 3번 손님은 C 서버... 이렇게 순서대로 돌아가며 배정합니다. 서버들의 성능이 모두 비슷하고, 요청이 처리되는 시간이 비슷할 때 아주 효과적입니다.
- **가중치 기반 라운드 로빈 (Weighted Round Robin):** 서버들의 성능이 다를 때 사용합니다. A 서버는 최신형 고성능 컴퓨터고, B 서버는 구형 컴퓨터라면? A 서버에게 '가중치'를 더 주어, A 서버에 3명을 보낼 때 B 서버에는 1명만 보내는 식의 융통성을 발휘하는 규칙입니다.
- **IP 해시 (IP Hash):** 클라이언트(사용자)의 IP 주소를 계산하여 항상 같은 서버로만 연결해 주는 방식입니다. 서울에서 접속한 '김코딩' 님은 항상 A 서버로만 배정받게 됩니다. 장바구니 데이터나 로그인 세션을 특정 서버에 유지해야 할 때 유용하게 쓰입니다.

---

### 2. 동적 로드밸런싱 (Dynamic Load Balancing)

동적 방식은 매니저가 **"현재 서버들이 얼마나 바쁜지 실시간으로 눈치를 보며"** 똑똑하게 손님을 나누는 방식입니다. 훨씬 유연하고 효율적이죠.

- **최소 연결 (Least Connection):** 현재 가장 '손님을 적게 응대하고 있는(연결 수가 가장 적은)' 서버에게 새 손님을 보냅니다. 어떤 손님은 밥을 빨리 먹고 나가지만, 어떤 손님은 한참 앉아있을 수 있죠? 라운드 로빈의 단점을 보완하여, 현재 가장 한가한 웨이터를 찾아 일을 줍니다. 동적 로드밸런싱의 가장 대표적인 방식입니다.
- **가중치 기반 최소 연결 (Weighted Least Connection):** '최소 연결' 방식에 서버의 성능(가중치)까지 고려한 콤보 방식입니다. 서버 성능에 비례하여 현재 연결 수가 가장 적당한 곳을 찾아줍니다.
- **최소 응답 시간 (Least Response Time):** 핑(Ping)을 날려봤을 때 "네, 부르셨어요!" 하고 가장 대답을 빨리하는 서버에게 트래픽을 보냅니다. 서버의 현재 연결 수뿐만 아니라, 네트워크 지연 상태 등 전반적인 건강 상태를 체크하여 가장 쌩쌩한 서버를 고르는 정밀한 방식입니다.

### 💡 한눈에 보는 로드밸런싱 아키텍처

아래 다이어그램을 통해 로드밸런서가 어떻게 클라이언트와 서버 사이에서 교통정리를 하는지 직관적으로 확인해 보세요.

```
graph TD
    Client1(사용자 1) --> LB{로드밸런서}
    Client2(사용자 2) --> LB
    Client3(사용자 3) --> LB
    
    LB -->|정적: 규칙대로 A로| ServerA[서버 A - 정상]
    LB -->|동적: 안 바쁜 B로| ServerB[서버 B - 여유]
    LB -->|동적: C는 바쁘니 패스| ServerC[서버 C - 과부하]
```

### 🚀 마무리하며: 어떤 방식을 선택해야 할까?

모든 상황에 완벽한 만능 알고리즘은 없습니다. 우리 서비스의 서버 성능이 모두 동일하고 트래픽 패턴이 단순하다면 설정이 간단하고 빠른 **정적 방식(라운드 로빈)**이 좋습니다.

하지만 사용자의 요청마다 처리 시간이 천차만별이고, 서버 상태를 실시간으로 모니터링하며 극강의 안정성을 추구해야 한다면 **동적 방식(최소 연결 등)**을 선택하는 것이 정답에 가깝습니다.

여러분도 프로젝트를 진행하며 서버를 여러 대 띄우게 된다면, 앞단에 Nginx나 AWS ELB 같은 로드밸런서를 붙여보고 오늘 배운 알고리즘들을 직접 적용해 보세요. 분명 짜릿한 경험이 될 것입니다!
