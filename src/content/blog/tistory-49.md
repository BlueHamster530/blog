안녕하세요.

백엔드 개발자로 성장하기 위해 데이터베이스(DB)를 공부하다 보면 가장 많이 듣는 조언이 쿼리가 느리면 인덱스(Index)를 걸어라입니다. 하지만 무턱대고 인덱스를 맹신하면 오히려 성능 저하를 겪을 수도 있습니다.

특히 게시판 검색 기능 등을 구현할 때 자주 사용하는 LIKE '%검색어%' 쿼리가 왜 인덱스를 타지 못하고 느린지, 그리고 인덱스가 많아지면 왜 데이터 저장(INSERT) 속도가 느려지는지 그 원리를 정확히 이해하는 것이 중요합니다.

오늘은 이 두 가지 주제를 사전과 도서관 사서에 비유하여 아주 쉽게 정리해 보겠습니다.

### 1. LIKE '%검색어%'가 느린 이유: 인덱스는 정렬된 사전이다

데이터베이스의 인덱스는 데이터를 가나다순(오름차순)으로 미리 정렬해 둔 목차와 같습니다. 우리가 국어사전에서 단어를 찾는 방식을 떠올려보면 이해가 쉽습니다.

**상황 A: LIKE '김%' (앞이 김으로 시작하는 사람 찾기)**

- 쿼리: SELECT \* FROM users WHERE name LIKE '김%';
- 동작: 사전을 펼쳐서 김 씨가 시작되는 페이지를 바로 폅니다. 그리고 김 씨가 끝나는 지점까지만 읽고 멈춥니다.
- 결과: 아주 빠릅니다. (Index Range Scan)

**상황 B: LIKE '%수' (뒤가 수로 끝나는 사람 찾기)**

- 쿼리: SELECT \* FROM users WHERE name LIKE '%수';
- 동작: 사전은 가나다 순으로 정렬되어 있지, 끝글자 순으로 정렬되어 있지 않습니다. 가수, 나수, 철수, 영수 같은 단어들이 사전 전체(ㄱ~ㅎ)에 흩어져 있습니다.
- 결과: 어쩔 수 없이 사전의 첫 페이지부터 끝 페이지까지 모든 단어를 하나하나 읽어서(Full Table Scan) 끝이 수인지 확인해야 합니다. 그래서 느립니다.

**전문 용어: Left-Most Prefix (좌측 접두사) 규칙** DB의 인덱스(B-Tree 구조)는 왼쪽 글자부터 비교하며 정렬합니다. 그런데 검색어의 왼쪽에 %(와일드카드)가 붙어버리면 정렬의 기준점이 사라지게 되어 인덱스를 사용할 수 없게 됩니다.

- LIKE 'abc%' : 가능 (시작점을 알 수 있음)
- LIKE '%abc' : 불가능 (시작점을 모름)
- LIKE '%abc%' : 불가능 (시작점을 모름)

따라서 본문 검색과 같이 %검색어% 패턴이 필요한 경우에는 Full Text Index(전문 검색 인덱스) 기능을 사용하거나, Elasticsearch 같은 별도의 검색 엔진을 도입하는 것이 올바른 해결책입니다.

### 2. 인덱스가 많으면 INSERT가 느린 이유: 도서관 사서의 고충

조회 속도를 높이기 위해 인덱스를 10개, 20개씩 막 만들면 어떻게 될까요? 이때는 데이터를 넣는 INSERT 속도가 현저히 느려집니다. 이것은 백엔드 시스템 설계의 대표적인 트레이드오프(Trade-off) 예시입니다.

이 현상을 도서관에 새 책이 들어오는 상황에 비유해 보겠습니다.

**상황 A: 인덱스가 없을 때 (빠름)** 데이터를 넣는 것은 책장에 책을 그냥 꽂아넣는 것과 같습니다. 빈 공간 아무 곳에나 책을 툭 던져 놓으면 끝이므로 아주 빠릅니다.

**상황 B: 인덱스가 많을 때 (느림)** 데이터를 넣는 것은 도서관의 분류 체계에 맞춰 책을 정리하는 것과 같습니다. 만약 인덱스가 3개(제목순, 작가순, 출판년도순) 걸려 있다면, 책 한 권(INSERT)이 들어올 때마다 사서는 4가지 일을 해야 합니다.

1. 책꽂이에 실제 책 넣기 (데이터 저장)
2. 제목순 목록 업데이트: 가나다 순서에 맞춰 목록 중간에 끼워 넣기
3. 작가순 목록 업데이트: 작가 이름 순서에 맞춰 중간에 끼워 넣기
4. 연도순 목록 업데이트: 연도 순서에 맞춰 중간에 끼워 넣기

**핵심 원리: 오버헤드(Overhead)** 인덱스는 항상 정렬된 상태를 유지해야 합니다. 따라서 데이터가 하나 추가될 때마다 인덱스(B-Tree) 구조를 다시 정렬하고 위치를 잡는 추가 작업이 발생하기 때문에 쓰기 속도가 느려지는 것입니다.

### 3. 결론: 인덱스는 공짜가 아니다

인덱스는 조회 성능을 얻는 대신, 쓰기 성능과 저장 공간을 지불하는 교환 행위입니다.

따라서 실무에서는 무작정 인덱스를 많이 만들지 않고, 서비스의 특성에 따라 전략을 다르게 가져갑니다.

- **조회(SELECT)가 많은 서비스:** 쇼핑몰 상품 목록이나 게시판 같은 경우 인덱스를 적극적으로 사용하여 조회 속도를 확보합니다.
- **쓰기(INSERT)가 많은 서비스:** 로그(Log) 수집이나 실시간 위치 추적 같은 경우 인덱스를 최소화하여 데이터 저장 속도를 확보합니다.

이러한 원리를 이해하고 상황에 맞춰 적절한 인덱스 전략을 세우는 것이 백엔드 개발자의 중요한 역량입니다.
