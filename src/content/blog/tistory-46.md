안녕하세요.

우리가 매일 사용하는 웹사이트들은 어떻게 내가 로그인했다는 사실을 기억할까요? 웹 통신 규약인 HTTP는 본래 상태를 저장하지 않는(Stateless) 특성이 있어, 페이지를 이동할 때마다 내가 누구인지 서버에 계속 알려줘야 합니다.

이때 사용자의 로그인 상태를 유지하는 방법은 크게 두 가지, 서버가 기억하는 세션 기반 인증과 클라이언트가 증명서를 들고 다니는 토큰 기반 인증으로 나뉩니다.

오늘은 이 두 방식의 작동 원리와 장단점을 명확하게 비교해 보겠습니다.

### 1. 세션 기반 인증 (Session-based Authentication)

세션 인증은 전통적인 방식이며, 서버가 사용자의 정보를 기억하고 있다는 점이 핵심입니다.

#### 작동 원리

1. 사용자가 아이디와 비밀번호로 로그인을 시도합니다.
2. 서버는 회원 정보를 검증한 후, 사용자의 고유한 ID를 생성하여 서버의 저장소(메모리 또는 DB)에 세션 ID라는 이름으로 저장합니다.
3. 서버는 이 세션 ID를 클라이언트(브라우저)에게 쿠키(Cookie)에 담아 보냅니다.
4. 이후 사용자가 다른 페이지를 요청할 때마다 브라우저는 쿠키에 있는 세션 ID를 자동으로 서버에 함께 보냅니다.
5. 서버는 전달받은 세션 ID가 자신의 저장소에 있는지 확인하여 유효한 사용자임을 인식합니다.

#### 비유: 헬스장 회원권과 사물함 키

세션은 헬스장 사물함 키와 같습니다. 회원은 카운터(서버)에 가서 회원임을 증명하고 사물함 키(세션 ID)를 받습니다. 회원이 헬스장 내 시설을 이용할 때마다 이 키를 보여주면, 직원은 키 번호를 대장(서버 저장소)과 대조해 보고 입장시켜 줍니다. 만약 키를 잃어버리면 직원은 대장에서 해당 번호를 지워버려(세션 만료) 더 이상 사용할 수 없게 만듭니다.

#### 장점

보안성이 높습니다. 서버가 세션 정보를 통제하므로, 해킹 의심 시 서버에서 해당 세션을 즉시 삭제하여 로그아웃시킬 수 있습니다. 구현이 상대적으로 명확하며 오랫동안 사용되어 레퍼런스가 많습니다.

#### 단점

서버의 부하가 큽니다. 접속자가 많아질수록 서버 메모리에 저장해야 할 세션 정보가 늘어납니다. 확장성이 떨어집니다. 서버를 여러 대(로드 밸런싱)로 늘릴 경우, A 서버에 로그인한 사용자가 B 서버로 요청을 보내면 B 서버에는 세션 정보가 없어 다시 로그인해야 하는 문제가 발생합니다. (이를 해결하기 위해 별도의 세션 저장소가 필요합니다.)

### 2. 토큰 기반 인증 (Token-based Authentication)

최근 모바일 앱과 최신 웹 서비스에서 많이 사용하는 방식입니다. 서버가 기억하는 대신, 인증되었다는 증명서(토큰)를 발급해 주고 클라이언트가 이를 보관합니다. 가장 대표적인 것이 JWT(JSON Web Token)입니다.

#### 작동 원리

1. 사용자가 로그인을 시도합니다.
2. 서버는 정보를 검증한 후, 사용자 정보를 암호화하여 토큰(Token)이라는 긴 문자열을 만듭니다. 이때 서버는 토큰을 따로 저장하지 않습니다.
3. 서버는 클라이언트에게 이 토큰을 전달합니다.
4. 클라이언트는 이 토큰을 로컬 스토리지나 쿠키에 저장해 둡니다.
5. 이후 요청을 보낼 때마다 헤더(Header)에 이 토큰을 실어서 보냅니다.
6. 서버는 토큰이 위조되지 않았는지만 검증(서명 확인)하여 사용자를 인식합니다.

#### 비유: 놀이공원 자유이용권 팔찌

토큰은 놀이공원 팔찌와 같습니다. 매표소(서버)에서 돈을 내면 입장권(토큰)을 줍니다. 놀이기구를 탈 때마다 이 팔찌만 보여주면 직원은 따로 장부를 확인하지 않고 팔찌의 유효성만 보고 통과시켜 줍니다. 매표소는 누가 들어왔는지 일일이 기억할 필요가 없습니다.

#### 장점

서버의 부담이 적습니다. 서버는 토큰을 저장하지 않고 검증만 하면 되므로 별도의 저장소가 필요 없습니다. 확장성이 뛰어납니다. 서버가 여러 대로 늘어나도, 토큰을 검증하는 방식(비밀키)만 알면 어떤 서버든 요청을 처리할 수 있습니다.

#### 단점

토큰을 탈취당하면 대처가 어렵습니다. 서버가 토큰을 저장하고 있지 않으므로, 해커가 토큰을 훔쳐서 사용해도 서버에서 이를 강제로 만료시키기 어렵습니다. (유효기간을 짧게 설정하여 피해를 줄입니다.) 전송 데이터량이 많습니다. 세션 ID는 짧은 문자열이지만, 토큰은 많은 정보를 담고 있어 길이가 길기 때문에 네트워크 트래픽을 더 많이 사용합니다.

### 마치며

정리하자면 다음과 같습니다.

세션 인증: 서버가 정보를 쥐고 있어 보안 관리가 중요하고 사용자가 적은 서비스에 적합합니다. 토큰 인증: 서버 확장이 필요하거나, 앱과 웹을 동시에 운영하는 대규모 서비스에 적합합니다.

어떤 방식이 무조건 더 좋다고 할 수는 없습니다. 서비스의 규모와 보안 요구사항에 맞춰 적절한 방식을 선택하는 것이 백엔드 개발자의 역량입니다.
